# Gortex evaluation — 2026-09-21

**Decision: do not enable Gortex v0.64.4 as a shared opt-in replacement for
native-ts.** It misses a renamed cross-file TypeScript caller that native-ts
finds. The failure persists after explicit re-indexing reports a complete,
healthy index. An incomplete caller list can hide affected code during a change.

The native-ts default, TLDR configuration, and both hosts' MCP registrations
remain unchanged. No Gortex installer, repository initializer, or login service
was installed. Gortex belongs in cc-settings if it passes a subsequent
evaluation; project-specific tracking and exclusions belong with each project.

## Tested release and method

- Release: [v0.64.4](https://github.com/zzet/gortex/releases/tag/v0.64.4), binary
  reports `v0.64.4+2b5480b`, built 2026-09-16.
- Platform: macOS arm64. Other platforms were not exercised.
- Release archive: `gortex_darwin_arm64.tar.gz`; SHA256 checked against the
  release's `checksums.txt` before extraction:
  `323995d1750239b10fb92d278a7c845b16b67ab0c268773a640dd662071b719c`.
- Native comparator: this repository's `src/codemap/cli.ts`.
- Small synthetic TypeScript and Python fixtures, with known declarations and
  callers; no live model requests or real-project workload benchmark.
- Isolated config, data, cache, Unix socket, PID, and log paths under `/tmp`.
  Telemetry was disabled. The daemon was stopped at the end.

## Results

| Check | native-ts | Gortex v0.64.4 |
|---|---|---|
| Direct TypeScript caller | Pass | Pass |
| Cross-file caller through a renamed import | Pass | **Fail: omitted caller** |
| Exclude unrelated same-named private declaration | Pass | Pass |
| Instantiated generic method caller | Pass | Pass |
| Missing-symbol query | No match | No match |
| Caller added by an edit | Fresh per invocation | Visible after 2 seconds |
| Small Python symbol and caller | Unsupported | Pass |

The real stdio MCP probe initialized successfully, negotiated protocol
`2025-03-26`, and identified server `gortex/0.64.4`. Under `nav/hide`, it listed
20 tools. A symbol search returned both same-named declarations with distinct
IDs. `edit_file` was absent from the list and a direct call was rejected with
JSON-RPC `-32601`; hiding the tool also prevented invoking it.

After the caller failure, an explicit re-index reported `status: ready`,
`index_complete: true`, `health_score: 100`, zero failed files, completed
TypeScript semantic enrichment, and `stale: false`. The renamed caller remained
absent from both caller and usage queries. This was not just a query issued
before the index was ready. A subsequently added direct caller appeared, so
watcher freshness did not explain the omission either.

Source inspection supports the observed cause: the
[free-function call resolver](https://github.com/zzet/gortex/blob/v0.64.4/internal/resolver/resolver.go#L3859)
looks up declarations by the call-site name, `renamed`, without translating it
to the imported export name, `auditedTarget`. The parser records the alias, but
the [alias translation helper](https://github.com/zzet/gortex/blob/v0.64.4/internal/resolver/npm_alias.go#L93)
is used for JSX resolution rather than this free-call path. Optional semantic
tooling may improve precision in other environments; it did not resolve this
case in the tested setup. A different query ID or a name-only query cannot
repair the missing association.

## Minimal failing case

Use a TypeScript project with `module: "esnext"`,
`moduleResolution: "bundler"`, `noEmit: true`, and `files` listing these files:

```ts
// a.ts
export function auditedTarget() { return 1; }
export function directCaller() { return auditedTarget(); }

// b.ts
import { auditedTarget as renamed } from "./a";
export function crossFileCaller() { return renamed(); }

// c.ts
function auditedTarget() { return 2; }
export function unrelated() { return auditedTarget(); }
```

Search for `auditedTarget` first and use the ID of the declaration in `a.ts`;
the fixture's repository prefix was `repo`:

```sh
gortex query callers 'repo/a.ts::auditedTarget' --index '/path/to/repo' --format json
bun '/path/to/cc-settings/src/codemap/cli.ts' context auditedTarget --project '/path/to/repo'
```

Expected callers: `a.ts::directCaller` and `b.ts::crossFileCaller`, excluding
`c.ts::unrelated`. Native-ts returned both expected callers. Gortex returned
only `repo/a.ts::directCaller`. After adding `freshCaller` to `a.ts`, Gortex
returned that new direct caller too, but still omitted the cross-file caller.

Session artifacts, including the isolated reproduction commands and MCP probe,
are retained at `/tmp/cc-gortex-eval/bench/`; these temporary files are not
repository dependencies.

## Measurements and limits

These are single-run observations on the tiny fixture, not performance targets:

| Operation | Observed |
|---|---:|
| Initial Gortex track/index | 0.57 s |
| First cold Gortex CLI symbol query | 3.68 s |
| Warm Gortex caller query after edit | 0.11 s |
| Native-ts context query | 0.48–0.55 s |
| MCP initialize | 163.01 ms |
| Native caller response after edit | 376 bytes |
| Gortex CLI caller response after edit | 1,836 bytes |

The response schemas and returned caller sets differ, so these byte counts are
not a like-for-like token-efficiency score. MCP stdout for initialization,
tool discovery, symbol search, and the rejected mutation totaled 60,358 bytes,
including schemas and duplicate text/structured result representations. No
token savings, model quality improvement, cache behavior, or cost savings were
measured. The isolated data directory included model assets; their delivery
mechanism was not established, so the run does not establish offline operation.

## Integration constraints for a passing release

Gortex must use its own `gortex` MCP namespace. The existing engine registry
promises the fixed `mcp__tldr__*` schema; Gortex's names and arguments do not
implement that contract. Its daemon commands also differ from TLDR's lifecycle.

The smallest integration uses the hosts' native MCP registration commands and
a preinstalled, verified binary. Routine cc-settings installs preserve these
independent entries. Codex rollback can restore an older complete `config.toml`,
including the MCP registrations in that snapshot. Adding another plugin to
the managed marketplace would require extending plugin ownership, source-copy,
backup, and uninstall behavior.

The [v0.64.4 tool policy](https://github.com/zzet/gortex/blob/v0.64.4/internal/mcp/tool_presets.go)
supports `GORTEX_TOOLS=nav` and `GORTEX_TOOLS_MODE=hide`. A future opt-in should
also set `GORTEX_AUTOINDEX=0`, `GORTEX_AUTOSTART=0`, and `GORTEX_TELEMETRY=0`,
and connect with `mcp --proxy` to an explicitly started daemon. This restricts
agent tools; it does not sandbox repository indexing.

Start the daemon from a neutral directory with an explicit configuration, then
track trusted repositories. Repository configuration can load grammars and
extractor programs or execute index transforms. Semantic enrichment can launch
language servers, and C# indexing can run `dotnet restore`.
`semantic.enabled: false` disables semantic enrichment in the daemon's config;
the MCP proxy's `--no-semantic` flag does not configure that shared daemon.
The older `mcp --index` and `--watch` options are no-ops in this release.
See the pinned [MCP command](https://github.com/zzet/gortex/blob/v0.64.4/cmd/gortex/mcp.go),
[index transforms](https://github.com/zzet/gortex/blob/v0.64.4/internal/indexer/transform.go),
and [language-server documentation](https://github.com/zzet/gortex/blob/v0.64.4/docs/lsp.md).

The next adoption gate is the same fixture with the renamed caller resolved,
plus repeated freshness, generic-method, missing-symbol, and restricted-MCP
checks. Passing those checks permits an opt-in trial; changing the default
requires representative project measurements beyond this small fixture.
